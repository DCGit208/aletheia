# Aletheia Project Delivery Plan

## Operating rule

This plan is updated as work proceeds. An item is marked complete only after its source, preservation, literary, pedagogical, experience, and technical checks have passed as applicable. See `PROJECT_EXCELLENCE_STANDARD.md` for the governing quality standard.

## 0. Controls and baseline

- [x] Review repository architecture, data model, access model, payment flow, deployment configuration, and content structure.
- [x] Review the five-page Aletheia Libraries 1 source leaflet in text and rendered form.
- [x] Review the owner decisions, source map, Scripture matrix, distinctions, student charges, crosswalk, and Foundation School writing standard.
- [x] Restore the failing content-quality guard before substantive learner-facing work.
- [x] Reconcile drift across code and documents: program grants, course handbook grants, Graphē inclusion, and reviewer identities.
- [x] Establish a per-unit traceability ledger recording source anchors, distinctions, charges, current contribution, proposed action, and verification outcome.

## 1. Learning architecture and delivery

- [ ] Confirm the Graphē is consistently presented as the entrance gate, never Course 1 of 6.
- [ ] Confirm the handbook, independent books, courses, and programs each have one unambiguous role.
- [ ] Confirm every course is complete in itself and books support rather than rescue lesson comprehension.
- [ ] Align product descriptions, checkout, success screen, library, program pages, and course pages with the same learner journey.
- [ ] Design and implement a genuine delivery boundary for paid text rather than shipping it in the public client bundle.

## 5. Alignment and experience pass

- [ ] Compare every course with its handbook chapter and related book.
- [ ] Remove only duplicative material that carries no unique teaching contribution.
- [ ] Add purposeful Scripture callouts, word-study panels, diagrams, timelines, and licensed/public-domain sacred art where they improve understanding.
- [ ] Refine typography, whitespace, mobile reading, progress, bookmarks, offline flow, navigation, and purchase-to-learning handoff.
- [ ] Complete desktop and mobile visual review for every changed screen.

## 6. Verification and release

- [ ] Run the content guard after each unit and resolve all failures before advancing.
- [ ] Run typecheck, lint, tests, and production build once the local dependencies are restored.
- [ ] Review every diff for accidental loss of doctrine, unsupported additions, access regressions, and visual degradation.
- [ ] Provide a review summary for each completed unit: preserved material, edits, rewrites, source basis, and verification results.
- [ ] Commit only a coherent, reviewed unit.
- [ ] Push `main`, verify the deployment/pipeline result, and verify the live learner experience.
